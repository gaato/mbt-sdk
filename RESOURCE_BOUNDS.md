# Resource bounds

This ledger covers JSON-RPC connections, Codex sessions and SDK-owned state.
HTTP engines, client admission, retry, pagination, cookies, multipart and SSE
limits are owned and tested by [mttp](https://github.com/gaato/mttp/blob/main/RESOURCE_BOUNDS.md).
Every enforced local limit names tests in its last column;
`moon run scripts/bounds_check.mbtx` verifies those references.


## Enforced limits

| Structure | Bound | On overflow | Tests |
|---|---|---|---|
| One JSON-RPC line (`jsonrpc/src/framer.mbt`, `LineFramer::feed`, `LineFramer::finish`; `jsonrpc-async/src/connection.mbt`, `Connection::start`) (#40, #49, #51) | `max_line` content bytes; the CR of a CRLF terminator is exempt. `Connection::start` defaults it to 64 MiB (`default_max_line`); `spawn_child` and codex-app-server's `spawn` and `connect` pass theirs through, so a Codex session has the same default. `LineFramer::new` on its own has no default: the transport sets it | `LineTooLong`, and the framer ends. Lines completed earlier in the same chunk are returned first and the error comes on the next `feed` or `finish`; `finish` also checks an unterminated last line. The read loop calls `feed(b"")` after each slice, turns it into `RpcFailure::Transport("JSON-RPC line exceeds N bytes")`, fails every pending call with that failure, and raises it into the group | `jsonrpc/src/framer_wbtest.mbt`: "max_line bounds line content, not the CRLF terminator", "an overflow delivers the lines completed before it, then raises once"; `jsonrpc-async/src/lifecycle_wbtest.mbt`: "LineTooLong fails pending requests with Transport and exits the group"; `jsonrpc-async/src/lifecycle_native_wbtest.mbt`: "lines are limited to 64 MiB when max_line is omitted"; `codex-app-server/src/client_test.mbt`: "max_line reaches the connection and an overlong reply fails the handshake" |
| JSON-RPC notification backlog (`jsonrpc-async/src/connection.mbt`, `Connection::start`, `notifications : @aqueue.Queue(kind=Blocking(max_notifications))`; `dispatch.mbt`, `Connection::dispatch`, `try_put`) (#49) | `max_notifications` notifications received but not yet passed to the sequential `on_notification` handler, default 32,768 (Codex emits up to 10,000 output deltas per command; its TUI buffers 32,768 events per thread); the one the handler holds is not counted. `spawn_child` and the Codex `spawn` and `connect` pass it through | The connection fails: `RpcFailure::Transport("JSON-RPC notification backlog exceeds N notifications")` to every pending call and the group. The read loop never waits for the handler instead, because a handler awaiting a call's response needs the read loop to deliver it | `jsonrpc-async/src/lifecycle_wbtest.mbt`: "a notification backlog over max_notifications fails the connection"; `jsonrpc-async/src/lifecycle_native_wbtest.mbt`: "the notification backlog is limited to 32,768 when max_notifications is omitted"; `codex-app-server/src/client_test.mbt`: "max_notifications reaches the connection and a stalled event handler fails it" |
| Inbound request handlers and reply-only tasks (`jsonrpc-async/src/dispatch.mbt`, `Connection::dispatch`, `Connection::reply_later`; `connection.mbt`, the `handlers` and `replies` semaphores) (#49, #51) | `max_inbound`, default 64, counted separately for request handlers running at once and for reply-only tasks (overload refusals, `id: null` errors for malformed lines) waiting to write. `spawn_child` and the Codex `spawn` and `connect` pass it through | A request past the handler limit is answered with `-32001` "Server overloaded; retry later." (Codex's own saturation error) without calling `on_request`, so a handler's outbound call never waits behind a blocked read loop. Past the reply limit the read loop waits for a reply task to finish, which depends only on the peer reading, not on any handler. A peer that writes without reading stalls the connection at `max_inbound` handlers, `max_inbound` replies, one partial line, and the rest of the lines framed from one slice of at most 64 KiB (`slice_bytes`; the read loop holds them while it waits for a reply permit), until the group ends. `Connection::start` frames each BinaryReader::read chunk in 64 KiB slices, dispatching a slice's lines before framing the next. BinaryReader::read has no size parameter, so the underlying reader owns the bound on the unframed remainder of one chunk | `jsonrpc-async/src/lifecycle_wbtest.mbt`: "a request past max_inbound is refused while handlers' own calls still complete", "a request past the default max_inbound of 64 is refused", "unread error replies hold the read loop at max_inbound until the peer reads", "a read's first lines are dispatched before the rest is parsed"; `codex-app-server/src/client_test.mbt`: "max_inbound reaches the connection and refuses a request past it" |

## Bounded by rate and lifetime

| Structure | Grows with | Bound |
|---|---|---|
| Codex child process (`codex-app-server/src/child.mbt`, `spawn`; `jsonrpc-async/src/child.mbt`, `spawn_child`, `Child::shutdown`) | stdout and stderr output | stdout is read continuously by the connection's read loop; stderr is inherited, never buffered here. The child and its pipes end with the caller's task group, and `shutdown` cancels the child after its timeout |

## Left to the caller

| Structure | Grows with | Why it is not bounded here |
|---|---|---|
| Pending JSON-RPC calls (`jsonrpc-async/src/connection.mbt`, `Connection::call`, `fail_pending`; `dispatch.mbt`, `Connection::dispatch`) | Calls the caller starts and the peer has not answered | The caller decides how many calls to start and how long each may wait: an entry leaves on its response or failure, on the call's `defer` (return, `timeout_ms`, cancellation), and all at once when the connection closes or reading ends. A caller that keeps calling without `timeout_ms` a peer that keeps the connection open but never answers grows the map without end, so such callers need deadlines or a cap on calls in flight. The Codex handshake has a 10 s deadline (`codex-app-server/src/client.mbt`, `initialize_connection`) |
| Streamed tool-call reassembly (`openai/src/types.mbt`, `ToolCallAccumulator::feed`; `anthropic/src/tools.mbt`, `ToolUseAccumulator::feed`) | The tool-call arguments of one stream, as the caller feeds the deltas | Arguments must be whole to be parsed. Each delta is within one SSE event's bound, but nothing caps their total: a request without a token limit, or an endpoint that keeps streaming while each read meets its timeout, grows the accumulator without end. The caller feeds it, so the caller caps it, by total events or accumulated bytes; set a token limit on the request as well |
| `Paginator::collect` | `max` | The caller states how many items it wants |
